# Photos requirements

Numbered, never reused. Each line names the test that proves it (`tests/…`), or `(not yet)`.
Source: the owner's request of 2026-11-06. Deployment-specific rules keep a one-line stub here.

- **PH1** The original Immich iPhone app works unchanged against this server: every endpoint it calls answers with the shape in `docs/immich-openapi-v3.3.6.json`; the server reports itself as Immich 3.3.6. Verified with the App Store app on a real iPhone (owner, 2026-11-19). *(tests/test_contract.py)*
- **PH2** Original files are never copied or moved. Scanning, thumbnails and downloads leave them byte-for-byte untouched; the only writes to the library are the ones the owner asks for in the app: delete (PH18) and, later, metadata edit (PH21). *(tests/test_readonly.py)*
- **PH3** A folder the owner picks is an album, and every photo and video inside it and inside all its subfolders belongs to that same album (no separate album per subfolder). Files added to or removed from the folder tree follow it. *(tests/test_albums.py)*
- **PH4** Faces are detected, grouped into people, and the owner can name, merge and split people (top priority). *(not yet)*
- **PH5** Search works in English. *(not yet)*
- **PH6** The Immich phone app cannot upload (its backup is refused with a clear error, so the camera roll is never mirrored); the only way in is the web app's Upload (PH58). *(tests/test_contract.py)*
- **PH7** Single user. Login is Immich's own (email + password, bearer token), no login proxy in front of the API. One password from the environment as `PHOTOS_PASSWORD` (or the first-run user, PH25); failed logins are rate-limited per client IP; the secret is never in the repo. *(tests/test_auth.py)*
- **PH8** Reachable like the real Immich: HTTPS through a reverse proxy; the app itself listens on loopback only. *(deployment-specific)*
- **PH9** Face/search models are downloaded once, then the app runs fully offline. *(not yet)*
- **PH10** Uses the GPU when present, else the CPU; the CPU path always works. *(not yet)*
- **PH11** Runs in Docker as uid 1000, read-only root, no capabilities, no new privileges. *(deploy check)*
- **PH12** An existing Immich instance and its data are never touched. *(deployment-specific)*
- **PH13** Stack: Python, Flask + gunicorn, pytest, like the other apps. *(repo layout)*
- **PH14** Memories: the app's Memories strip ("on this day" per year, from asset dates) works: list, open, and the assets in each. *(not yet)*
- **PH15** Explore shows People (named and unnamed, with face thumbnails) and opens a person's photos. *(not yet)*
- **PH16** Explore shows Places: photos with GPS are grouped by city/place and openable, and the map markers work. Reverse geocoding uses a place dataset downloaded once, then offline (PH9). *(not yet)*
- **PH17** Favorites: the owner can mark a photo as favorite; only its identity (content hash, plus path as a hint) is stored in a JSON file in the data dir. No copy of the image is ever made. *(tests/test_favorites_trash.py)*
- **PH18** Delete (photos only, one or several picked by hand (PH40); never a folder or album): after a confirmation the file is moved to a trash folder outside the library (`DATA_DIR/trash/`, with a record of its original path), so a sync tool such as Syncthing removes it on every device; Restore puts it back at the original path; the trash empties after 30 days. The library is mounted read-write for this, and nothing else may write there. *(tests/test_favorites_trash.py)*
- **PH19** The web app uses the Desktop flavour of the Design Language (sidebar of albums), light and dark, fully usable on a phone. *(index.html; checked by screenshot at 1280 and 390 px)*

- **PH20** A "Photos" view like Immich's `/photos`: every photo of every album on one big scrolling timeline (grouped by month/day, with a scrubber), as an option next to the per-album view. *(index.html; scrubber rail, per-month lazy load)*
- **PH21** (future) Edit a photo's metadata (date, description, location) without losing any existing EXIF/ICC data; to be decided whether it writes into the file or into an own store. *(not yet)*
- **PH22** The folders in `PHOTOS_DEFAULT_ALBUMS` are already picked at first start; an album the owner un-picks stays gone after a restart. *(tests/test_hardening.py)*
- **PH23** Scanning never blocks a request: a picked folder is indexed in a background thread with progress (`/ui/scan`), rescanned every 10 min so albums follow the folder; measured on 18,000 photos: first scan 7 s, no-change rescan 0.9 s, a month of the timeline 11 ms. Overlapping picks (a folder and its subfolder) both stay complete. *(tests/test_albums.py, tests/test_hardening.py)*
- **PH25** First run: with no user (and no PHOTOS_PASSWORD) the login screen creates the single user (scrypt-hashed in DATA_DIR; once only).
- **PH29** People: offline face detection (OpenCV YuNet + SFace, models baked into the image), faces grouped into people, name/merge/hide, "not this person", People page and person filter, Immich-shaped /api/people.

- **PH31** Explore page: Memories ("N years ago": photos within 3 days of today in earlier years), People, Places (GPS from photos and videos, offline nearest-city lookup); Immich-shaped /api/memories.

- **PH24** A launcher page links to the app. *(deployment-specific)*
- **PH33** Hidden photos: like Favorites, a photo can be hidden (viewer button, Tools menu, right-click, or the app's "locked" visibility). Hidden photos are out of the timeline, albums and counts, formats, favorites, memories, places, People, search and the phone sync. They live in a "Hidden" album opened only after the PIN. Marks are stored by content hash in `hidden.json` (like favorites, survive renames) plus a table the queries use; the files are never touched. *(tests/test_hidden.py)*
- **PH34** The Hidden PIN is chosen on the sign-up form (4 to 12 digits, optional); with none set it is 12341234 and the album says so. Stored scrypt-hashed. Unlocking (`POST /api/auth/session/unlock`) lasts 15 idle minutes per login, can be locked at once (`/session/lock`, Tools menu) and is rate-limited (5 wrong in 15 min per IP). The PIN changes with the current PIN or the password (`/api/auth/pin-code`), and a hidden photo's thumbnail, original, metadata and faces answer 403 while locked. *(tests/test_hidden.py)*
- **PH35** People you do not care about: "Don't show more" on each person card hides them from People (and "Show again" in the hidden list); no photo is touched. *(index.html; checked in browser)*
- **PH36** Phone sync: `POST /api/sync/stream` (+ `/sync/ack`) streams the library in the spec's shapes so the Immich app can build its timeline (user, assets, exif, albums, album-to-asset, memories, people, faces); unchanged since the last ack = only SyncCompleteV1, else SyncResetV1 and the full current state. Also the app's start-up calls (preferences, storage, statistics, partners, notifications, stacks, tags, search by metadata). Verified on a real iPhone (owner, 2026-11-19). *(tests/test_mobile.py)*
- **PH37** Sign in on another device by QR code (File menu): one-time, 5 minutes, only points back at this server; the Immich app still signs in with email and password. *(tests/test_hidden.py)*
- **PH38** fail2ban: every failed login, PIN or QR attempt is written to `DATA_DIR/auth.log` with the client IP; `deploy/fail2ban/` holds the filter and jail (5 in 15 min, 1 hour). Needs root to install; a ban only covers clients the host firewall sees. *(tests/test_hidden.py + fail2ban-regex)*
- **PH39** Video playback: a video the browser cannot decode (3GP/H.263/AMR, AVI, WMV, FLV...) is played from a cached H.264/AAC MP4 made in `DATA_DIR/playback/`, the original file never touched; browser-ready files (H.264/VP9/AV1 in MP4/MOV/WebM) are sent as-is. *(tests/test_playback.py)*
- **PH40** Multi-select delete: the Select button (or Ctrl/Cmd-click, Shift-click for a range) picks several photos; one confirmation with the count moves them all to the trash (restorable, PH18) via `POST /ui/assets/delete` (needs `confirm: true`, 1 to 1000 asset ids). *(tests/test_favorites_trash.py)*
- **PH41** Viewer shows the names of the named people in the open photo as chips over the bottom of the picture; tapping a name closes the viewer and opens that person's photos. Unnamed faces are not listed (they stay in Info). *(index.html; checked in browser)*
- **PH42** Hidden means hidden everywhere (review 2026-11-06): the clip of a hidden Live Photo, the face crops of a hidden photo, a deleted hidden photo in Trash (list, thumbnail, restore) and the converted copy of a hidden photo all need the PIN; a hidden photo restored from the trash comes back hidden (a favorite comes back a favorite). Hidden responses are sent `Cache-Control: no-store`. *(tests/test_review_regressions.py, tests/test_review_fixes.py)*
- **PH43** Sign-in hardening: logins expire after 90 unused days (sliding, `PHOTOS_TOKEN_DAYS`); `/api/sessions` lists them and `DELETE /api/sessions/<id>` (or `/api/sessions` for every other device) revokes them; the cookie is `photos_session` (Immich, on the same host, owns `immich_access_token`, still read for old logins); each failed attempt reserves its slot under a lock, a password tried at the PIN endpoints also counts against the login limit, idle addresses are forgotten; responses carry X-Frame-Options DENY, nosniff and a CSP with `script-src 'self'` (the page's script is `/app.js`; no inline script or handlers); fail2ban reads the log as UTC (`logtimezone`), and the access log names the real client (X-Forwarded-For). *(tests/test_review_fixes.py)*
- **PH44** Library follows the files: cached thumbnails, full-size renders and playback copies are named after the file's mtime (a replaced file gets new ones) and stale ones are pruned; a folder that cannot be read never deletes its photos; an album un-picked during its scan stays gone; a scan reads files with no transaction open and writes in short batches; delete commits the database before moving the file; dates of videos and files without EXIF are local time like EXIF dates; people are recounted when their photos go (count, centroid, cover; empty ones removed); background work starts with the server, not on the first request, and idle workers write nothing. *(tests/test_review_regressions.py, tests/test_review_fixes.py)*
- **PH45** Cheap and bounded: at most 3 image decodes and 1 ffmpeg encode at a time; HEIC thumbnails use the embedded preview; full-size HEIC/TIFF renders are cached; the web app plays every video's original first (HEVC included) and only on a decode error asks for an H.264 copy made in the background (`/ui/playback/<id>?state=1`, polled), Live Photo auto-play never starts one; ffprobe verdicts are cached; conversions are capped at 100 MP output; memories are one grouped query, asset lists load rotations/live/hidden once; the phone's sync resends at once for a change in assets, hidden, live pairs, rotations, albums or favorites (hashes of ids, not counts) but at most hourly for faces, people and places alone. Compose: CPU limit (`PHOTOS_CPUS`), healthcheck, capped logs. *(tests/test_review_fixes.py)*
- **PH46** Conversions keep metadata: EXIF (TIFF too), ICC and XMP are carried into JPG/PNG/WebP/TIFF, EXIF pixel dimensions follow a resize, MOV/AVI to MP4 keeps Apple's QuickTime keys (`use_metadata_tags`); BMP holds none. ffmpeg/ffprobe run with `-protocol_whitelist file,pipe`; the face models are pinned to an opencv_zoo commit and sha256-checked at build. *(tests/test_review_fixes.py, tests/test_review_regressions.py)*
- **PH47** Background upkeep (review follow-ups #26, #35, #38): one low-priority thread makes the grid thumbnails of photos that have none (newest first, one render at a time) and the SHA-1 of every file (base64, Immich's `checksum`, so the phone can match its camera roll; reads throttled, a changed file is hashed again); until then the asset id stands in. When the face worker is idle (at most every 6 h, only if faces were added) unnamed groups that are clearly one person are joined (average linkage on centroids, cosine >= 0.45); named people, hidden people and merges are never changed, and a face moved out with "Not this person" (remembered in `face_not`) never joins that group again. The face worker keeps the centroid matrix in memory during a pass. *(tests/test_review_fixes.py)*
- **PH48** Live Photos play by themselves, once, 3 seconds after the photo opens in the viewer (muted, never starting a conversion); on by default, switched off and on again with the "Play Live Photos automatically" menu item (stored in `localStorage.photos_liveauto`, only "0" means off). - **PH49** Tag a person on a photo: the viewer's **Tag** button (menu Tools/View entry, right-click, key T) lists only people who already have a name (searchable); after picking one the owner clicks the face and `POST /ui/assets/<id>/faces {personId, x, y}` (fractions of the picture as shown, app rotation undone by the server) either gives the detected face under the point to that person (the old person gets `face_not`, so re-clustering does not undo it; refused with 409 if it is the old named person's only face) or adds a small hand-placed face there (`face_manual`, survives a re-scan). ## Deep dive (2026-11-24)

- **PH96 — Deleting a second file from the same path keeps the first one in the trash.** An asset's id comes from its path, so a photo deleted, replaced by a new file of the same name (an upload, Syncthing) and deleted again went into the same trash folder and overwrote the first one: it could no longer be restored. - **PH97 — A damaged video cannot hang conversions.** `convert_video` read ffmpeg's progress (stdout) to the end before reading stderr; a damaged file prints a line per bad frame, the 64 KB stderr pipe filled, ffmpeg stopped, and the conversion waited forever while holding the one transcode slot, so every later conversion and every playback copy waited behind it. ffmpeg's stderr now goes to a temporary file; its last lines are still the error message. *(tests/test_deep_dive_2026_11_24.py::test_ph97_a_chatty_ffmpeg_cannot_deadlock_a_video_conversion, ::test_ph97_ffmpeg_error_text_still_reported)*
